## 🚀 快速参考

### 什么时候用什么技能？

```bash
# 规划阶段 - 制定计划
/harness-plan create

# 实现阶段 - 执行实现
/harness-work all

# 同步阶段 - 检查进度
/harness-sync

# 状态查询 - 快速确认
/harness-sync --no-retro
```

### 一句话职责

| 技能 | 一句话职责 | 何时使用 |
|------|-----------|---------|
| `harness-plan` | **制定计划** - 从想法到任务分解 | 需要开始新项目或功能规划时 |
| `harness-work` | **执行实现** - 从任务到代码实现 | 需要实现已计划的任务时 |
| `harness-sync` | **同步状态** - 对照计划与实现 | 需要检查进度或更新状态时 |

## 🎯 技能职责概览

### harness-plan: 规划专家

**核心职责**: 制定计划，不写代码

```
✅ 能做什么:
   • 制定项目计划和任务分解
   • 技术选型和架构设计
   • 需求分析和优先级排序
   • 创意探索和方案设计

❌ 不能做什么:
   • 修改任何源代码文件
   • 执行构建或测试命令
   • 分析 git 状态和实现历史
   • 修改配置文件

📁 操作范围:
   ✅ Plans.md, spec.md, docs/
   ❌ src/, app/, lib/, pkg/
```

### harness-work: 实现专家

**核心职责**: 执行实现，不制定规划

```
✅ 能做什么:
   • 修改源代码文件
   • 执行构建和测试命令
   • 分析 git 状态和实现历史
   • 管理工作区和分支

❌ 不能做什么:
   • 修改任务定义 (Task/内容/DoD)
   • 改变任务优先级
   • 添加或删除任务
   • 修改产品规格

📁 操作范围:
   ✅ 任意文件 (实现需要)
   ❌ 修改 Plans.md 的 Task/内容/DoD 字段
```

### harness-sync: 状态专家

**核心职责**: 同步状态，不做决策

```
✅ 能做什么:
   • 分析 Plans.md 与实现的差异
   • 更新任务状态标记
   • 执行进度回顾分析

❌ 不能做什么:
   • 修改任务定义
   • 修改源代码
   • 执行实现操作

📁 操作范围:
   ✅ Plans.md (仅限状态更新)
   ❌ 代码文件和规划文档
```

## 📖 详细使用指南

### 场景 1: 开始新项目

**正确流程**:

```bash
# Step 1: 制定计划 (规划阶段)
/harness-plan create
> 输入想法和需求
> 生成技术选型和架构设计
> 输出: Plans.md + spec.md

# Step 2: 实现功能 (实现阶段)
/harness-work all
> 接收已批准的 Plans.md
> 执行代码实现和测试
> 输出: 实现代码 + 更新的 Plans.md

# Step 3: 检查进度 (同步阶段)
/harness-sync
> 分析实现与计划的差异
> 更新任务状态标记
> 输出: 状态更新的 Plans.md
```

**错误示例** ❌:
```bash
# 错误: 在规划技能中执行实现
/harness-plan create --implement-code
> 这会违反技能边界，规划技能不能修改代码

# 错误: 在实现技能中修改任务定义
/harness-work --modify-task-definition
> 这会违反技能边界，实现技能不能修改任务定义
```

### 场景 2: 添加新功能

**正确流程**:

```bash
# Step 1: 添加到计划
/harness-plan add "实现用户认证功能"
> 分析需求和技术选型
> 添加任务到 Plans.md
> 输出: 新任务 (Task 16.1)

# Step 2: 执行实现
/harness-work 16.1
> 实现用户认证功能
> 执行测试和验证
> 输出: 实现代码

# Step 3: 同步状态
/harness-sync
> 确认任务完成
> 更新状态标记
> 输出: cc:完成
```

### 场景 3: 检查项目进度

**正确流程**:

```bash
# 查看详细进度分析
/harness-sync
> 完整的进度同步 + 回顾分析
> 输出: 详细进度报告

# 快速查看状态
/harness-sync --no-retro
> 仅状态同步，跳过回顾
> 输出: 简洁状态报告
```

## 🚫 边界违规示例

### 违规示例 1: 规划时修改代码

**场景**: 用户想快速实现功能，在规划时直接修改代码

```bash
# ❌ 错误操作
/harness-plan create
> 在规划过程中直接修改 src/UserService.java
> **违规**: harness-plan 不能修改源代码

# ✅ 正确操作
/harness-plan create
> 完成规划，生成 Plans.md
/harness-work all
> 使用 harness-work 实现代码
```

### 违规示例 2: 实现时修改任务定义

**场景**: 实现过程中发现任务描述不准确，直接修改

```bash
# ❌ 错误操作
/harness-work 15.1
> 发现任务定义不准确，直接修改 Plans.md 的 Task/内容字段
> **违规**: harness-work 不能修改任务定义

# ✅ 正确操作
/harness-work 15.1
> 完成实现，在 Plans.md 中添加注释说明发现的问题
> 记录到 Issues 或调用 harness-plan 重新规划
```

### 违规示例 3: 在规划中分析实现细节

**场景**: 规划时过度分析实现历史

```bash
# ❌ 错误操作
/harness-plan create
> 执行 git log 详细分析
> 分析 agent traces 查看实现历史
> **违规**: harness-plan 不能进行深度实现分析

# ✅ 正确操作
/harness-plan create
> 专注于需求分析和任务分解
> 实现分析交给 harness-sync
```

## 🔍 边界检测和纠正

### 自动边界检测

系统会自动检测以下违规行为：

| 违规类型 | 检测规则 | 处理方式 |
|---------|---------|---------|
| 代码修改 | 检测 src/ 文件操作 | 自动阻止 + 警告 |
| 构建执行 | 检测构建命令 | 自动阻止 + 警告 |
| Git 分析 | 检测 git status/log | 自动阻止 + 警告 |
| 任务修改 | 检测 Plans.md Task 字段修改 | 自动阻止 + 警告 |

### 手动检查清单

**使用 harness-plan 后检查**:
- [ ] 没有修改源代码文件
- [ ] 没有执行构建或测试
- [ ] 所有修改都在规划文档范围内
- [ ] 生成的 Plans.md 完整且格式正确

**使用 harness-work 后检查**:
- [ ] 没有修改任务定义
- [ ] 代码实现符合任务 DoD
- [ ] 状态更新基于实际完成情况
- [ ] 发现的问题已正确记录

## 🛠️ 故障排除

### 问题: "规划技能在修改代码"

**症状**: 使用 `/harness-plan` 时发现代码文件被修改

**原因**: 边界检测可能失效，或者使用了错误的技能

**解决方案**:
1. 立即停止当前操作
2. 检查应该使用 `harness-work` 而非 `harness-plan`
3. 使用 `/harness-sync` 检查当前状态
4. 使用正确的技能重新执行

### 问题: "实现技能在修改任务定义"

**症状**: 使用 `/harness-work` 时发现 Plans.md 任务定义被修改

**原因**: 可能是越界操作或者技能边界不清晰

**解决方案**:
1. 检查是否需要重新规划
2. 将发现的规划问题记录下来
3. 使用 `/harness-plan add` 或 `update` 处理规划变更
4. 继续使用 `harness-work` 执行实现

### 问题: "不确定使用哪个技能"

**症状**: 有一个任务，不知道该用哪个技能

**决策流程**:

```bash
# 第一步: 判断任务性质
任务是否涉及代码修改？
是 → 使用 harness-work
否 → 继续判断

# 第二步: 判断是否需要规划
任务是否需要任务分解？
是 → 使用 harness-plan
否 → 继续判断

# 第三步: 判断是否需要状态同步
任务是否需要更新状态标记？
是 → 使用 harness-sync
否 → 可能不需要 Harness 技能
```

### 问题: "技能报告边界违规"

**症状**: 系统报告 "Boundary violation detected"

**原因**: 当前操作违反了技能边界

**解决方案**:
1. 查看违规详情和类型
2. 使用正确的技能重新执行
3. 如果确实需要该操作，考虑是否需要重新规划

## 📚 最佳实践

### 1. 明确的使用顺序

**推荐流程**:
```
规划 → 实现 → 同步 → 规划调整 → 实现 → 同步
```

1. **规划阶段**: 使用 `harness-plan` 制定完整计划
2. **实现阶段**: 使用 `harness-work` 执行所有任务
3. **同步阶段**: 使用 `harness-sync` 更新状态
4. **迭代**: 如需调整，从步骤1开始

### 2. 清晰的职责分离

**记住**:
- **规划** = 做什么 (What)
- **实现** = 怎么做 (How)
- **同步** = 做得怎样 (How well)

### 3. 正确的状态更新

**规则**:
- `harness-plan`: 创建任务，初始状态 `cc:TODO`
- `harness-work`: 实现过程中更新 `cc:WIP`，完成后更新 `cc:完成`
- `harness-sync`: 验证状态，标记修正建议

### 4. 处理发现的问题

**发现规划问题**:
- 记录到 Plans.md 注释
- 标记相关任务为 `blocked`
- 使用 `harness-plan` 重新规划

**发现实现问题**:
- 记录到 Plans.md 注释
- 继续实现或标记为 `blocked`
- 使用 `harness-sync` 分析影响

## ❓ 常见问题

### Q: 为什么需要这么严格的技能边界？

**A**: 清晰的技能边界确保：
- **可预测性**: 用户知道每个技能会做什么
- **可维护性**: 技能可以独立开发和维护
- **可测试性**: 可以验证技能是否正确工作
- **协作性**: 技能间可以无缝协作

### Q: 如果我发现技能在错误地工作怎么办？

**A**: 请检查：
1. 是否使用了正确的技能
2. 是否有边界违规警报
3. 是否需要更新到最新版本
4. 如果问题持续，请报告 issue

### Q: 可以在实现过程中调整计划吗？

**A**: 可以，但需要：
1. 使用 `harness-work` 记录发现的问题
2. 使用 `harness-plan` 调整计划
3. 使用 `harness-sync` 同步状态
4. 继续使用 `harness-work` 执行实现

### Q: 边界检测会影响性能吗？

**A**: 边界检测经过优化：
- 静态分析在技能加载时执行一次
- 运行时检测开销 < 5%
- 对整体性能影响可忽略
